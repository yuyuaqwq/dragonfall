## 5. 亮点（≥2 条）

1. **装配顺序显式纪律**：game/data/_assembly.py 头部注释（1-7 行明写"先派生表再 build_index"）+ `data/__init__.py:94` 末尾 `from . import _assembly` 的载入时机安排，以及 `MAP_BY_ID` 由 MAPS 单一数据源重建（_assembly.py:114-117），把多源失步/历史手写副本问题统一收口——这是好的装配设计。
2. **循环引用隔离手法系统化**：12+ 个 core 模块统一采用"函数内延迟 `from .. import db`""`from .. import content as C`"等技法（development.md:25、affix_effects.py:30 注解、battle_mech.py:284/353 等），并留下踩坑注释（wild.py:14-15、exploration.py:14-15），把循环风险逐点标明。
3. **store 层方向干净**：game/store/（含 game/db.py 聚合）未出现任何 core/data/commands 反向 import（grep 无匹配），commands 对 store 的依赖（social.py:24）符合架构"commands 依赖 store"。隔离方向单向成立，是唯一没有反向依赖的层。
4. **索引域演进清晰**：v48"key 即 ID 不再二次转拼音"的 guard（core/index.py:36-39、_assembly.py:149 注释）、v104 M24 怪物索引覆盖规则注释详细，可追溯意图。

## 6. 相邻切面核对结论（交叉核对矩阵 4.1：M1↔M2 分层与存储实现一致性）

- M1 侦测到 store→core/data/commands **无**反向 import（即 M2 职责域未被上层越界反向污染），且 M1 中 core 对 db 的全部直读都经 `game/db.py`→`store/__init__.py` 聚合层，落在 M2 的存储实现面上——两者在"何处碰 DB"上**一致**：唯 store 暴露 DB 接口，core 以延迟导入复用该接口。结论：分层与存储实现方向一致，但"core 以 db 别名反复直读"这一事实（见 A-1）是 M1 的分层缺陷而非 M2 的实现缺陷，需经组长转达 M2 复核这些读路径的事务/白名单纪律（尤其 achievement_conds/title_conds 等高频查询是否走 store 白名单，属于 M2 侧检查项）。
